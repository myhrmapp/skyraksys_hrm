# SkyrakSys HRM Help and Support Guide

This is the active support guide for the current implementation. It reflects the runtime behavior implemented in the repo and intentionally does not rely on archived project notes or historical deployment artifacts.

## Active documentation scope

- This guide is intended for end users, administrators, and support staff.
- The live application help is also exposed through the in-app User Guide at /user-guide and the manifest in [frontend/public/guides/guide-manifest.json](../frontend/public/guides/guide-manifest.json).
- Historical materials under [archive](../archive) remain historical only and are not used as the live support path.

## 1. Employee management help

### Supported behavior
- Admin and HR users can add, update, and review employee profiles.
- Employee IDs are stored in the employeeId field as unique identifiers and are expected to follow the SK-nnnn pattern as seeded in the default demo data.
- The employee profile includes personal, employment, emergency, statutory, and banking information.
- Employee login creation is handled as a separate account flow for eligible users.

### Support guidance
- Use Employees > Add Employee to create a new record.
- Use the profile tabs to review or edit work details, statutory information, and banking details.
- If a login is not yet created, create the account from the user account section before handing access to the employee.
- For onboarding issues, verify the email is unique, the hire date is valid, and required fields are completed before submission.

### Common issues
- Duplicate employee email or employeeId values are rejected by validation and database uniqueness rules.
- Invalid PAN, Aadhaar, IFSC, or PIN formats produce field-level validation errors.

## 2. Leave help

### Supported behavior
- Employees can submit leave requests, managers can approve or reject them, and employees can cancel pending requests.
- Approved leave reduces the relevant leave balance according to the leave type and business rules.
- Rejected or cancelled requests restore the relevant balance.
- Leave balances are tracked by employee and leave type for the active year.

### Support guidance
- Use My Leave to submit a request and review current balances.
- Managers review pending requests from the Leave Management area.
- Approval, rejection, and cancellation actions update the request status and associated balance records.

### Common issues
- Leave not showing in balances after approval usually means the leave type mapping or balance update failed.
- Cancellation or rejection should restore the balance; if it does not, check the related leave balance record and status transition logic.

## 3. Attendance help

### Supported behavior
- Attendance records are created for check-in and check-out workflows and support correction or review flows.
- Admins and managers can review attendance records and handle exceptions or corrections.

### Support guidance
- Use the attendance module to review employee attendance status.
- For a correction, locate the record in the attendance list and apply the change with the correct approval path.
- Ensure the employee is assigned to the correct date and shift context before correcting a record.

## 4. Timesheet help

### Supported behavior
- Timesheets are tracked by employee and period and may be submitted, reviewed, and approved by managers.
- The system supports status transitions for timesheet review and approval workflows.

### Support guidance
- Employees submit their scheduled work through the My Timesheet flow.
- Managers review and approve or reject entries from the timesheet review area.
- If timesheet data appears stale after approval, confirm the updated status was persisted and the employee record is still active.

## 5. Payroll help

### Supported behavior
- Payroll is calculated from salary structures and generated through the payroll service layer.
- Sensitive payroll fields are protected by the server-managed encryption vault and not exposed in plaintext outside authorized flows.
- Payslips are generated by the backend and can be delivered through the payroll workflow.

### Support guidance
- Confirm the employee has a valid active salary structure before generating a payroll run.
- Review payslips only through approved payroll access paths.
- Do not copy sensitive payroll values into tickets or external chat channels.

### Common issues
- Payroll generation will fail if the employee data, salary details, or required vault configuration is incomplete.
- Missing or unsafe vault values should block startup rather than continue in a degraded state.

## 6. Invoice help

### Supported behavior
- Invoice generation uses encrypted invoice data and a secret phrase header for access control.
- The invoice workflow includes client records, line items, PDF generation, and encrypted payload handling.
- Invoice access is intentionally gated by the configured invoice secret phrase.

### Support guidance
- Ensure INVOICE_SECRET_PHRASE is configured before invoice generation.
- Do not share the secret phrase outside the authorized admin or backend operations flow.
- If invoice data is masked, this indicates the request did not include the required secret and the system intentionally hid sensitive content.

## 7. Notifications and broadcasts help

### Supported behavior
- Notifications and system broadcasts are supported through the backend notification service and Socket.io channels.
- Role-based and department-aware notification flows exist for real-time updates.

### Support guidance
- Use the notification center or admin broadcast area to issue user- or role-targeted updates.
- If a broadcast does not reach the intended audience, review the target role, department, and event channel configuration.

## 8. Performance and goals help

### Supported behavior
- Employees and managers can manage goals and key results, and progress can be tracked through the related performance modules.

### Support guidance
- Review goals, key results, and their status from the performance area.
- Check progress values and linkage to employees or teams when a goal appears stale or incomplete.

## 9. Admin and system settings help

### Supported behavior
- System settings cover application configuration, email settings, support-related configuration, and general admin control.
- The deployment model is Docker Compose with an internal PostgreSQL service and a public Nginx entry point.

### Support guidance
- Keep the active production environment file validated before deployment.
- Review admin settings only after confirming the environment and database are healthy.
- Do not enable pgAdmin or other tooling unless the production path explicitly requires it.

## 10. Security and RBAC help

### Supported behavior
- Protected routes require JWT-based authentication and role checks.
- The system validates required production secrets before startup and fails closed when placeholders or weak values remain.
- The repo intentionally avoids shipping insecure default secrets in the active production configuration template.

### Support guidance
- Treat secret rotation as a production change process.
- Verify secrets are not present in archived scripts, support notes, or local developer files before release.
- Follow the active deployment path instead of legacy or archive instructions.

## 11. Operational support and deployment help

### Supported behavior
- The canonical deployment flow is Docker Compose from the repo root.
- The migration script applies schema changes through the running backend container.
- The app health endpoint is expected to return healthy when the container is running correctly.

### Support guidance
- Use the active deployment flow from [README.md](../README.md) and [docs/DEPLOYMENT.md](DEPLOYMENT.md).
- Apply DB migration changes with the repo-supported migration script before restarting the backend.
- If the app fails to start, review environment validation output and ensure required production variables are populated.

## 13. Escalation and support path

- For user support issues: start with the relevant module workflow in this guide.
- For configuration and deployment issues: check the active deployment docs and required secrets validation output.
- For production security or access-control issues: escalate to the security and system admin owners before any broad rollout or data export.
- Keep private credentials out of tickets, logs, and Chat messages.
